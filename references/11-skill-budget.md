# 11 · 技能体量预算与整合协议

> 技能会随着「再加一个系统 / 再加一个品牌 / 再补一条规则」持续膨胀，直到：
> 触发词互相重叠、SKILL.md 变成百科、每次加载都烧掉一半上下文。
> 本章规定**体量预算**与**整合时的适应性调整**——新增内容前先想清楚它属于哪一层、挤掉了什么。

---

## 1. 三层加载模型

| 层 | 何时加载 | 放什么 | 预算 |
|---|---|---|---|
| **T0 always** | 每次会话 | `SKILL.md`（路由 + 铁律 + 门禁） | ≤ 160 行 / 16 KB |
| **T1 on-demand** | 进入对应阶段才读 | `references/*`（单主题，按 P0–P8 路由） | 单文件 ≤ 340 行 / 42 KB；总计 ≤ 170 KB / 14 个 |
| **T2 data** | 被具体条目命中才查 | `brand-specs/`、`systems/`、`example/`、`data/*.json` | 不设行数，按目录体积上限 |

原则：
1. **T0 只放「不做就会错」的规则**；细节、清单、逐品牌数据一律下沉。
2. **T1 按阶段拆分**：一个文件只服务 1–2 个阶段；跨 3 个阶段就拆。
3. **T2 永不整体加载**：`brand-specs/` 3.8 MB、`systems/` 快照，只能按 id 取单条。

## 2. 整合协议（每次新增东西都走这 5 步）

```text
1. 分类：它是路由（T0）、规则（T1）、还是数据（T2）？
2. 落位：能改路由解决就不加文件；能加 T1 就不动 T0。
3. 去重：和现有哪条重叠？合并、替换，还是明确「不和它重复」？
4. 裁剪：这次新增挤掉了什么？删一条旧规则、拆一个过胖文件、或退休一个触发词。
5. 测量：node scripts/check-skill-size.mjs —— 超预算不合并。
```

### 三种整合模式（选一种，并在 `skill-budget.json` 登记）

| 模式 | 适用 | 动作 | 例 |
|---|---|---|---|
| **Router-only** | 只是多一个分支/关键词 | 只改 `SKILL.md`/`00` 的路由，不加文件 | 「微信小程序」加一个触发词 |
| **On-demand reference** | 需要一套规则，但只在某阶段用 | 新增 1 个 T1 文件 + 路由指向它 | `references/10-official-systems.md` |
| **Data snapshot** | 是可枚举的数据（品牌/系统/组件） | 放 T2，加索引，不给 T0/T1 增负 | `systems/astryx/`、`brand-specs/` |

**一个 release 最多做 1 个整合**；两个以上必须拆版本，否则无法归因体量变化。

## 3. 预算表（与 `skill-budget.json` 同步）

| 项 | 上限 | 当前 |
|---|---|---|
| `SKILL.md` | 160 行 / 16 KB | 125 行 / 12.2 KB |
| 触发词 | 20 | 17 |
| T0 文件数 | 1 | 1 |
| references | 14 个 / 170 KB | 12 个 / 约 125 KB |
| 单 reference | 340 行 / 42 KB | 01b 最大 261 行 |
| templates | 14 | 12 |
| scripts（根 `.mjs`） | 10 | 7 |
| brand-specs | 6 MB | 3.8 MB |
| examples | 6 MB | 3.7 MB |
| systems | 2 MB | 0.1 MB |

超预算的处理顺序：**拆（split）→ 删（retire）→ 下沉（T1→T2）→ 提预算（最后手段，需写理由）**。

## 4. 退化（decay）策略

每次发版做一次 5 分钟审计：

- **触发词**：连续两个版本没被任何场景用到的，删。
- **reference**：如果一个文件只被一个阶段引用、且 < 60 行，考虑并入相邻文件。
- **规则**：同一类禁止项超过 3 条时，合并成一条 + 子项。
- **数据**：品牌/系统快照每季度复核一次上游许可与版本；过期的归档而不是留着。
- **重复**：`SKILL.md` 与 reference 出现同一句话 = 冗余，T1 留细节、T0 留指针。

## 5. 案例：这两次整合怎么做的

### v1.1.0 · 接入 Astryx（On-demand + Data）

- 分类：组件/token 是数据（T2），选择规则是 T1。
- 落位：新增 `systems/astryx/`（T2）+ `references/10`（T1）；`SKILL.md` 只加了 4 行（P1 基座、读入顺序、脚本表）。
- 去重：没有把 Astryx 塞进 10 个风格族（那是「风格」，不是「实现」），避免污染品牌路由。
- 测量：T0 未超；T1 +1 文件（当时未超）。
- **结果**：功能进来了，但 P1 的加载量没变。

### v1.2.0 · 拆分 01（Adaptive split）

- 症状：`01-brand-taxonomy.md` 涨到 483 行 / 38 KB，P1 每次全量加载。
- 动作：拆成「路由层 01（162 行 / 15 KB）」+「逐族细节 01b（261 行 / 20 KB，选定候选族后再读）」；删掉与 `brand-index.json` 重复的 58 品牌附录。
- 效果：P1 首次加载 −46%（50.7 KB → 27.4 KB）；细节仍在，但不拖累路由。
- 这就是「**整合时做适应性调整**」：不是把新内容加进去就完事，而是重新分配层级、把体量挪到该在的层。

## 6. 怎么测量

```bash
node scripts/check-skill-size.mjs            # 人读表格 + PASS/FAIL
node scripts/check-skill-size.mjs --json -   # 机器可读
```

- 退出码：0 全部在预算内；1 有超预算项；2 用法错误。
- CI 每次 push 都跑；超预算即红，必须先裁剪。
- `skill-budget.json` 是唯一预算真源；改预算 = 改这个文件 + 在 PR/commit 里写理由。

## 7. 反模式

- ❌ 「先加进去，以后再说」——以后不会来。
- ❌ 把逐品牌/逐组件数据粘进 reference（应放 T2 数据）。
- ❌ 每个新功能都往 `SKILL.md` 加一段（应加 T1 + 一行路由）。
- ❌ 预算超了直接调高上限（先拆/删/下沉）。
- ❌ 触发词只增不减（用户说「做前端」时，20 个触发词等于没有触发词）。
