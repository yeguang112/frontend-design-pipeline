# 02 · frontend-guidelines 规范与版本迭代

> `design/frontend-guidelines.md` 是项目的**唯一设计权威**：它同时回答「要做什么」和「不许做什么」。
> 本文件规定它的结构、写法、版本化、签收与冲突裁决。模板见 `templates/frontend-guidelines.md`。

---

## 1. 定位

| 它是什么 | 它不是什么 |
|---|---|
| 用户已签收的设计契约 | 一次性生成的设计说明 |
| 可被脚本/人逐条检查的规则集 | 形容词合集（「高级」「现代」「有质感」） |
| 版本化的活文档（v0.1 → v1.0） | 写完就锁死的文档 |
| 与 tokens / components 对齐的规则层 | tokens 的重复描述（值只在 tokens 里） |

**三条不可违背**：
1. 规则必须**可判定**：每条都能回答「怎么检查它有没有被执行」。
2. 规则必须**有例外**：写清例外条件，否则规则会被绕过。
3. 规则只能**升版本**修改：任何修改追加决策日志，不静默改。

---

## 2. 文件结构（9 节，顺序固定）

```md
# Frontend Guidelines · <项目名>

## 0. 元信息
版本 / 日期 / 状态（draft|signed|frozen）/ 端 / 设计读法 / 风格族 / 主辅参考
## 1. 设计目标与受众
一句话目标 + 3 条成功标准 + 明确不做什么（non-goals）
## 2. 设计表盘
VARIANCE / MOTION / DENSITY + 每个值对布局的具体含义
## 3. 品牌参考边界
keep / change / do-not-copy 三段表
## 4. 正面清单（MUST）
MUST-01… 每条：规则 / 判定方法 / 例外
## 5. 反面清单（NEVER）
NEVER-01… 每条：禁止项 / 为什么 / 判定方法 / 例外 / 修复建议
## 6. 交付范围
端（web/app/mini-program）/ 屏清单 / 状态清单 / 响应式档位 / 主题
## 7. 变更授权与流程
谁可以改、改前读什么、改后跑什么、何时需要用户批准
## 8. 验收定义
客观项（脚本+阈值）+ 主观项（用户签收）+ 不通过的处理
## 9. 决策日志索引
指向 decision-log.md，并列出关键转折（v0.1 初稿 / v0.3 否掉玻璃 / v1.0 冻结）
```

## 3. 正面清单的写法

每条格式：

```md
- **MUST-03 一屏一个视觉焦点**
  - 规则：每屏只有一个主视觉层（标题/主图/主数据），其余元素降级为辅助。
  - 判定：首屏截图中，字号最大与第二大的元素有明显层级差（≥1.4×）；主 CTA 与次 CTA 视觉权重不同。
  - 例外：品牌站允许「双焦点」对称构图，但必须在 guidelines 中写明。
```

写法要求：
- **动词开头**，一句能读完。
- **判定**必须能落到：截图目测（给比例/位置）、CSS 检查（给属性）、脚本（给阈值）。
- **例外**必须写条件，不写「视情况而定」。
- 数量建议 **10–18 条**；超过 20 条说明在写组件规范，不是设计准则。

推荐覆盖的正面维度（按需取）：
1. 一个视觉焦点
2. 网格与对齐（8pt/4pt 基准）
3. 单一强调色与使用上限
4. 一套圆角系统
5. 字体家族 ≤2 + 明确档位
6. 真实内容与真实图片
7. 全状态（hover/focus/active/disabled/loading/empty/error）
8. 对比度 AA
9. 键盘可达 + 可见焦点
10. 动效时长/曲线统一 + reduced-motion
11. 响应式三档 + 无横向溢出
12. 语义化 DOM / 可读的 alt
13. token-first（禁裸值）
14. 组件复用优先于新建

## 4. 反面清单的写法

反面清单是本链条最有价值的部分——它把「AI 味」变成**可检测的禁令**。完整库见 `03-negative-list.md`，此处只规定写法。

每条格式：

```md
- **NEVER-07 紫色/蓝紫渐变（作为默认强调）**
  - 禁止：hero 底色、按钮、标题文字使用紫→蓝/靛→品红渐变。
  - 为什么：LLM 默认审美（Tailwind indigo #6366f1 系）的典型指纹。
  - 判定：`detect-drift.mjs` 规则 `ai-purple-gradient`；或人工查 gradient 色相 250–300°、饱和度 >60%。
  - 例外：主参考品牌的设计规范明确把紫作为品牌色，且只用于规范指定位置（例如 Linear 的 #5e6ad2 平面强调），不得做成渐变或外溢到其他页面。
  - 修复：改单一中性底 + 一个高对比强调色；或改用品牌规范里的 accent。
```

要求：
- 每条必须有 **ID + 检测方式**，能进 `detect-drift.mjs` 的写规则名。
- 「为什么」一句话即可，用于说服用户与自我约束。
- 例外必须**收窄**（谁能用、用在哪、用多少），不能是「品牌需要时可用」。

**反面清单与 tokens 的关系**：反面清单管「不许出现的模式」，tokens 管「允许出现的值」。二者冲突时以更严格者为准。

## 5. 版本与迭代协议

### 5.1 版本号

| 版本 | 含义 | 谁签 |
|---|---|---|
| `v0.x` | 草案，可大改 | AI 提案，用户反馈 |
| `v1.0` | 用户签收，成为权威 | 用户 |
| `v1.x` | 签收后的追加/细化（不改变方向） | 用户确认变更点 |
| `v2.0` | 方向性改版（换风格族/换主参考/换表盘） | 用户明确要求 |

### 5.2 迭代循环（P2 ↔ P3 之间可多轮）

```text
AI 出 v0.1（正/反清单 + 表盘 + 参考边界）
   ↓ 用户反馈（喜欢/不喜欢/补充）
AI 出 v0.2（只列 diff：新增/删除/修改了哪几条，为什么）
   ↓ 用户确认
… 直到用户说「就这个」
AI 标 v1.0 + 状态 signed，并在 decision-log 记录签收原文
```

**diff 规则**：每次迭代只展示变化，不重贴全文；变化必须能追溯到某条用户反馈。

### 5.3 决策日志（`design/decision-log.md`）

每轮一条：

```md
### 2026-11-07 · v0.1 → v0.2
- 用户反馈原文：「不要玻璃那种，太假」
- 变更：新增 NEVER-12（玻璃拟态滥用）；MUST-05 改为「实底优先」
- 影响：原第 3 屏 hero 的半透明卡片需改实底
- 未解决：用户对圆角大小仍不确定，暂定 12px
```

价值：**这就是「沉淀到全过程」**。长期项目里，新会话的 AI 读决策日志即可恢复用户口味，不必重问。

## 6. 用户反馈的三种处理

| 反馈 | 判读 | 动作 |
|---|---|---|
| 「就这个 / 可以 / 确认」 | 签收 | 升 v1.0，状态 signed，进 P3 |
| 「第 X 条不对 / 改成 Y」 | 执行层修正 | 改该条 → v0.x+1 → 只报 diff |
| 「说不上来，就是不好看」 | 方向或执行不确定 | 给 2–3 个可视觉化对比（品牌/做法），或先做 1 屏 A/B 静态稿；**禁止盲改 5 版** |

**禁止**：把「说不上来」当成「随便改」，连续生成 3 版以上还不问用户。

---

## 7. 冲突裁决

按优先级从高到低：

1. **用户当次明确指令**（「这次就要紫色」）——但必须写进 guidelines 例外，不能只存在于对话里。
2. **冻结的 HTML**（视觉真相）——当规则描述与冻结稿不一致，以冻结稿为准，然后修正规则文字。
3. **tokens**（数值真相）——当代码里的值与 tokens 不一致，以 tokens 为准。
4. **frontend-guidelines**（规则真相）——当上述三者都不涉及，按 guidelines 判。
5. **品牌规范（参考层）**——只提供方向，不 override 上述任何一层。

发现 2/3 层冲突时，**必须**改规则或改 token，不允许「两边都留着」。

---

## 8. 反模式

- ❌ 规则写成形容词：「要高级」「要克制」「要有呼吸感」——无法判定。
- ❌ 正面清单 40 条、反面清单 3 条——失衡，AI 只会背正面清单。
- ❌ 反面清单没有例外——遇到合理需求时整条规则被弃用。
- ❌ guidelines 里重复写具体色值/字号——应该只写角色名并指向 tokens。
- ❌ 用户口头同意就算签收，没记录原文——后续争议无从追溯。
- ❌ 为了通过验收而改规则（而不是改实现）——这是最严重的作弊。

---

## 9. 最小可用清单（10 + 10，可直接作为 v0.1）

**正面（MUST）**：一个视觉焦点 / 8pt 网格对齐 / 单一强调色 ≤2 处/屏 / 一套圆角 / 字体 ≤2 家族 / 真实内容 / 全交互状态 / AA 对比度 / 可见焦点 / token-first。

**反面（NEVER）**：紫蓝渐变 / 玻璃拟态滥用 / 大圆角卡片滥用 / 三张等宽功能卡 / emoji 当图标 / 渐变文字与发光 / 假数据假截图 / 居中 hero + 深色 mesh / 装饰性 pill 与编号 eyebrow / 衬线滥用（Fraunces / Instrument Serif 作默认）。

> 完整版（含判定与例外）见 `03-negative-list.md`。
